## 2. 画面遷移と状態機械

画面は **1ページ内の状態遷移** で完結させる。ルーティングによる画面切り替えは行わない。
理由は、演出の連続性(入力欄が上にスライドしてそのまま投稿カードに変わる)を保つため。

| state | 画面の見え方 | 次の遷移 |
|---|---|---|
| `idle` | 入力欄が画面中央。プレースホルダと投稿ボタンのみ | テキスト入力で `composing` |
| `composing` | 文字数カウンタ表示、投稿ボタンが活性化して色づく | 投稿タップで `posting` |
| `posting` | 入力欄がフェードアウトし、投稿カードが下から迫り上がる(0.6s) | 自動で `reacting` |
| `reacting` | 反応がタイムラインで積み上がる。カウンタが回り、リプライが降ってくる。**体験の本体** | タイムライン完了で `settled` |
| `settled` | 数字が確定し、画面下部にスクショ案内と「もう一度」が出現 | 「もう一度」で `idle` |

> **設計上の注意**
> `reacting` 中もユーザーはスクロールできる状態にしておく。演出を「見せられている」のではなく
> 「自分のタイムラインを眺めている」感覚にするため、操作をロックしない。
>
> **2026-08-20 改訂: 投稿カードの `position: sticky` は撤回する。**
> 常に上部に貼り付いていると画面上部が固定要素だらけ(ヘッダー+投稿カード)になり、
> リプライを読める領域が狭くなる。本家Xも投稿詳細で投稿カードを固定しない。
> **投稿カードは普通にスクロールアウトさせる。**

## 3. 演出タイムライン仕様

体験の心臓部。全体の尺は **約12秒**。「静か→さざなみ→爆発→余韻」の4フェーズ構成にする。
ここを一定速度で伸ばすと退屈になるため、必ず段差をつける。

### Phase A: 静寂 (0.0 – 1.2s)

投稿カードが出現し、カウンタはすべて 0。まだ何も起きない。
この「間」があるからこの後の爆発が効く。カードのみ軽くスケールイン(1.02 → 1.0)。

### Phase B: さざなみ (1.2 – 3.5s)

エール数が 0 → 数十へゆっくり。リプライが1〜2件、間隔をあけて降ってくる。
ここでのリプライは「短くて素朴な人格」を優先的に出す(例: 後輩キャラの一言)。通知音は小さめ。

### Phase C: 爆発 (3.5 – 8.0s)

エール数が指数的に加速し、最終値の約90%まで一気に到達。ひろめる数も追随。
リプライが 0.3〜0.6s 間隔で連続投下され、ハートが画面下部から次々飛ぶ。
バイブレーション(`navigator.vibrate`)を短く連打。**音の主張が最も強い区間。**

### Phase D: 余韻 (8.0 – 12.0s)

加速が緩み、残り10%をゆっくり詰めて最終値で止まる(easeOut)。
リプライ投下も間隔が開いていき停止。

**8.5s 以降にインプレゾンビが2〜3体、0.4s以内の短い間隔で連投される。**
最後に「トレンド入りしました」風のバッジがふわりと出現して `settled` へ。
`settled` 遷移後、未翻訳のゾンビリプライを600ms間隔で自動展開する(オチを確実に見せるため)。

### 数値の設計

最終値は毎回同じだと飽きるためランダム化する。ただし **各指標を独立にランダム抽選してはいけない。**
実際のSNSでは各数値の間に安定した比率が存在するため、独立に振ると
「いいね2万なのにリポスト30」のような、見た瞬間に嘘だと分かる組み合わせが生まれる。

**エール(いいね)を基準に、他の指標を比率で導出する**のが本仕様の原則。

#### 抽選ロジック

#### 基準にした実データ

実際にバズったXの投稿の実測値(2026-08 時点で観測):

| # | いいね | リポスト | リプライ | 表示回数 | リポスト率 | リプライ率 | いいね率 |
|---|---|---|---|---|---|---|---|
| A | 1.6万 | 264 | 31 | 209万 | 1.7% | 0.2% | 0.77% |
| B | 1.5万 | 830 | 46 | 372万 | 5.5% | 0.3% | **0.40%** |

感覚的に想像するより、リポストもリプライも**桁違いに少ない**。ここを盛ると即座に嘘だとバレる。

> **観測Bで いいね率のレンジを 0.6% → 0.4% まで広げた。**
> 観測Aだけだと 0.77% を中心に置いていたが、Bは 0.40% とその約半分だった。
> いいね率は投稿の性質で倍近く振れる値なので、下限を 0.4% まで下げて幅を持たせる。
> リポスト率も A 1.7% / B 5.5% と3倍以上開くため、1.5〜6% のレンジ設定は妥当と確認できた。

```ts
const yells       = randInt(8_000, 24_000);                   // 基準値
const engageRate  = randFloat(0.004, 0.015);                  // いいね率 0.4〜1.5%
const impressions = Math.round(yells / engageRate);           // 表示回数
const spreads     = Math.round(yells * randFloat(0.015, 0.06));
const replyCount  = Math.max(
  30,
  Math.round(yells * randFloat(0.005, 0.025))
);
const bookmarks   = Math.round(yells * randFloat(0.08, 0.15));
```

| 指標 | 導出 | 実際の値域 | 根拠 |
|---|---|---|---|
| **エール(いいね)** | `randInt(8000, 24000)` | 8,000 – 24,000 | 「バズった」と実感でき、かつ非現実的でない範囲 |
| **表示回数(インプレ)** | `yells / 0.4〜1.5%` | 約 53万 – 600万 | 実測いいね率 0.40〜0.77% を含む幅 |
| **ひろめる(リポスト)** | `yells × 1.5〜6%` | 120 – 1,440 | 実測1.7%と5.5%。**盛りたくなるが我慢する箇所** |
| **リプライ件数** | `yells × 0.5〜2.5%`(下限30) | 40 – 600 | 実測0.2%だが、褒め投稿はリプライが伸びやすいのでやや上振れさせる |
| **保存(ブックマーク)** | `yells × 8〜15%` | 640 – 3,600 | 実測 1705/1.5万 = 11.4% |
| 表示リプライ数 | `randInt(8, 12)` | 8 – 12 件 | スクショに収まる範囲。多すぎると1件ずつ読めず価値が下がる。**インプレゾンビ2〜3体を含む内数** |

> **表示リプライ数とインプレゾンビの関係**
> 表示リプライ数はゾンビを **含む** 内数とする。ただし4章の「1周目で6人格を一巡させる」を必ず満たすため、
> **通常人格は最低6件を確保し、ゾンビ数はその残り枠に収まるよう切り詰める**（例: 表示8件ならゾンビは最大2体）。
> ゾンビを外数にすると最大15件になり、スクショに収まらなくなるためこの方式を採る。

> **リプライ件数に下限30を設けた理由**
> 実測比率をそのまま使うと、表示リプライ数(8〜12件)よりリプライ総数のほうが少なくなる場合がある。
> 「リプライ12件」と表示されているのに12件全部見えているのは不自然なので、必ず総数が上回るようにする。

> **なぜ表示回数を追加したか**
> 「いいね1.2万」だけでは、それが何人に届いた結果なのかが分からない。
> 表示回数があることで初めて「42万人に見られた」という規模の実感が生まれる。
> Xでも表示回数は投稿詳細で必ず表示される要素であり、無いとむしろ不自然。

#### リプライ1件ごとの指標

本家はリプライにも1件ずつアクション行と数値が付く。ここが無いと画面がスカスカに見えるため、
リプライにも指標を持たせる。観測Bのリプライ実測値:

| いいね | リポスト | 返信 | 表示回数 |
|---|---|---|---|
| 670 | 50 | 2 | 41万 |
| 597 | 46 | 1 | 40万 |
| 368 | 24 | 1 | 36万 |

```ts
// likeCount は人格ごとのレンジ（04_褒めセリフ集.md）で決まっている前提
const replyReposts     = Math.round(likeCount * randFloat(0.06, 0.09));
const replyReplies     = Math.round(likeCount * randFloat(0.001, 0.005));
const replyImpressions = Math.round(parentImpressions * randFloat(0.08, 0.15));
```

| 指標 | 導出 | 根拠 |
|---|---|---|
| リポスト | `likeCount × 6〜9%` | 実測 7.5% / 7.7% / 6.5% |
| 返信 | `likeCount × 0.1〜0.5%` | 実測 0.30% / 0.17% / 0.27%。**ほぼ0になるのが正しい** |
| 表示回数 | **親投稿の表示回数 × 8〜15%** | 実測 41万/372万 = 11%。いいね数から導出すると破綻するのでこちらを使う |

> **0 は数字を出さない。** 本家はカウント0のときアイコンのみを表示する。
> インプレゾンビ（likeCount 2〜40）はリポストも返信もほぼ0になり、
> 「誰にも相手にされていない」様子がそのまま数字に出る。**これは狙いどおりなので補正しない。**

#### 表示位置(2026-08-20 改訂・本家スマホアプリ準拠)

**数値の置き場はアクション行1箇所だけにする。** 本家がそうなっているため。

```
午後10:23 · 2026年8月19日 · 42.8万 件の表示
────────────────────────────────────
 💬 847   🔁 2,104   ♡ 12,438   🔖 1,705   ⬆
```

- 表示回数は時刻行に併記する(本家どおり)。アクション行には**入れない**
- 保存(ブックマーク)数を新設する。本家のスマホアプリには必ず表示されている

> **旧仕様(3カウンタの巨大メトリクス行)を撤回した理由**
> エール数を大きく見せるため、時刻行の下に `エール / ひろめる / リプライ` の
> 3カウンタを独立した行として置いていた。しかしこれは本家に存在しない要素で、
> **その下のアクション行から数字が消えてアイコンだけが並ぶ**という、
> 本家では絶対に起きない見た目を生んでいた。
> 数値をアクション行に集約し、メトリクス行は廃止する。
> カウントアップ演出の主役性は「エール数だけフル桁表示＋`like` 色」で担保する
> → [03_デザイントークン.md](03_デザイントークン.md) 6章

#### 数値フォーマット規則

| 値域 | 表記 | 例 |
|---|---|---|
| < 10,000 | 3桁区切り | `8,432` |
| 10,000 – 999,999 | 万・小数第1位 | `1.2万` / `42.8万` |
| ≥ 1,000,000 | 万・整数 | `124万` |

**ただしエール数(主役)だけは例外で、常に3桁区切りのフル表示にする。**

> **理由が2つある。**
> (1) カウントアップ演出は桁数が多いほど気持ちいい。「1.2万」では数字がほとんど動かず、
> 演出の主役が一番地味になってしまう。
> (2) カウントアップ中に `9,999 → 1.0万` と表記形式が切り替わると、
> 桁数が急に減って「数字が戻った」ように見える。

#### カウントアップの実装

- GSAPで数値オブジェクトを `tween` し、`onUpdate` で `Math.floor` して描画する
- 数字要素には `font-variant-numeric: tabular-nums` を必ず指定する。指定しないと桁が変わるたびに横幅が揺れて品位が落ちる
- 表示回数はエールより **わずかに先行して** 伸ばす。「見られた結果いいねが付く」という因果に合わせると自然になる

## 4. リプライ人格の設計

褒めセリフは「誰が言っているか」で刺さり方が変わる。人格を6種定義し、各人格ごとにテンプレート群を持たせる。

表示リプライは 8〜12 件なので、6人格を一巡させたあと2周目に入る。
**1周目では人格を重複させず、2周目以降も同一セリフは絶対に重複させない。**
また、人格ごとに出現可能な時間帯を制約する(素朴な反応 → 熱狂 → 権威づけ → 見知らぬ人の共感、の順序を作るため)。

| 人格ID | キャラ | 口調・特徴 | 出現フェーズ |
|---|---|---|---|
| `kouhai` | 素直な後輩 | 短く、感嘆。「えっすごい」「尊敬します…」 | B(早い) |
| `shinyu` | テンション高い親友 | タメ口・絵文字多め・全肯定 | B–C |
| `senpai` | 面倒見のいい先輩 | 具体的に褒める。「そこに気づけるのが偉い」 | C |
| `mom` | おかん的存在 | 健康を気遣いつつ褒める。「ちゃんと寝るんだよ」 | C |
| `pro` | その道のプロ | 冷静に価値を言語化する。認証バッジ付きで表示 | C(後半) |
| `stranger` | 通りすがりの他人 | 知らない人からの共感。「わかる、それ本当にえらい」 | C–D |
| `zombie` | インプレゾンビ | **アラビア語**で連投。翻訳すると全力で褒めている | D(2〜3体) |

### テンプレート設計ルール

- ユーザー入力を `{{deed}}` として埋め込むテンプレートと、埋め込まない汎用テンプレートを両方用意する
- **埋め込み型は全体の3割まで。** 入力文が「ゴミを捨てた」のような短文だと日本語として破綻しやすいため、汎用テンプレートを主軸にする
- 各人格につき最低8パターン。合計50パターン以上を目標にする
- 否定・比較・アドバイスは一切入れない。「褒める」だけに徹する

→ 全文は [04_褒めセリフ集.md](04_褒めセリフ集.md)

## 5. データモデル(TypeScript)

Phase 1で他の演出を追加することを見越し、`ReactionScenario` を演出パターンの共通インターフェースとして定義する。
X型はその一実装にすぎない。

```ts
// ---- 演出パターンの識別子 ----
export type PerformanceKind = "x" | "line" | "instagram";

// ---- 人格 ----
export type PersonaId =
  | "kouhai" | "shinyu" | "senpai" | "mom" | "pro" | "stranger"
  | "zombie";            // インプレゾンビ（アラビア語）

export interface Persona {
  id: PersonaId;
  displayName: string;   // 表示名（例: "みなみ"）
  handle: string;        // @minami_0203
  avatarSrc: string;     // /avatars/kouhai.png
  verified: boolean;     // pro のみ true
  templates: string[];   // {{deed}} を含みうる
}

// ---- 生成されたリプライ1件 ----
export interface ReactionItem {
  id: string;
  persona: Persona;
  body: string;          // テンプレート展開済みの本文
  appearAt: number;      // 演出開始からの ms
  likeCount: number;     // このリプライ自体につくエール数

  /** 本文の言語。"ar" のとき RTL 表示 + 翻訳UIを出す */
  lang: "ja" | "ar";
  /** lang === "ar" のときのみ存在。「翻訳を表示」で出る日本語 */
  translation?: string;

  /** このリプライのアクション行に出す指標。0 のときは数字を表示しない */
  repostCount: number;      // likeCount × 6〜9%
  replyCount: number;       // likeCount × 0.1〜0.5%
  impressionCount: number;  // 親投稿の impressions × 8〜15%
}

// ---- 数値カウンタの目標値 ----
// すべて yells から比率で導出する。独立にランダム抽選してはいけない。
export interface MetricTargets {
  yells: number;         // いいね相当（基準値・主役）
  impressions: number;   // 表示回数。yells / 0.6〜1.5%
  spreads: number;       // リポスト相当。yells × 1.5〜6%
  replyCount: number;    // リプライ総数（表示用）。yells × 0.5〜2.5%（下限30）
  bookmarks: number;     // 保存相当。yells × 8〜15%（実測 1705/1.5万 = 11.4%）
}

// ---- 1回の演出の完全な設計図 ----
export interface ReactionScenario {
  kind: PerformanceKind;
  deed: string;              // ユーザーの入力
  targets: MetricTargets;
  items: ReactionItem[];     // appearAt 昇順
  totalDurationMs: number;   // 通常 12000
  trendLabel: string;        // 例: "エール数 急上昇1位"
}

// ---- 状態機械 ----
export type StageState =
  | "idle" | "composing" | "posting" | "reacting" | "settled";
```

> **重要な設計判断**
> `ReactionScenario` は投稿ボタンを押した瞬間に **全件まとめて生成する**。演出中に逐次ランダム生成しない。
> 理由は2つ。
> (1) 途中で人格が重複するバグを構造的に防げる。
> (2) 演出の再生・リプレイ・将来の共有画像生成が、同じシナリオを再生するだけで実現できる。

## 6. コンポーネント構成

「演出を再生するコンポーネント」と「見た目のコンポーネント」を分離する。
前者にロジックを集約し、後者は `props` を受け取って描画するだけの純粋な存在にする。

| コンポーネント | 責務 | 状態を持つか |
|---|---|---|
| `StageContainer` | StageState の管理と各画面の出し分け。演出全体の司令塔 | 持つ |
| `DeedComposer` | 入力欄・文字数カウンタ・投稿ボタン。idle / composing を担当 | 入力値のみ |
| `Header` | Yロゴ。53px固定・sticky | 持たない |
| `PostCard` | ユーザーの投稿カード。**固定せず普通にスクロールする** | 持たない |
| `ActionBar` | アクション行。**カウンタの表示先を兼ねる**。仕様は [03_デザイントークン.md](03_デザイントークン.md) 4章・4-2章 | 持たない |
| `TimestampLine` | 時刻 · 日付 · 表示回数。表示回数カウンタを含む | 持たない(ref経由) |
| `ReplyList` | リプライを appearAt に従って順次マウント | 持たない |
| `ReplyCard` | リプライ1件。アバター・名前・本文・エール数 | 持たない |
| `TranslateToggle` | ゾンビリプライの「翻訳を表示」。展開状態を持つ | 展開フラグのみ |
| `HeartBurst` | 画面下部から飛ぶハート。Canvas または絶対配置DOM | 持たない |
| `TrendBadge` | Phase D で出る「急上昇1位」バッジ | 持たない |
| `ResultActions` | settled で出るスクショ案内と「もう一度」 | 持たない |

### ロジックの置き場所

- `buildScenario(deed)` — 純粋関数。`ReactionScenario` を組み立てる。**Reactに一切依存させない**(単体テストが書けるように)
- `useReactionTimeline(scenario)` — カスタムフック。GSAPのタイムラインを構築し、状態遷移を発火する
- `useSound()` — 効果音の再生を一元管理。初回タップ時にAudioContextを解錠する処理を含む

## 8. 音の仕様(Phase 0 では実装しない)

> **2026-08-20 決定: Phase 0 に音は入れない。**
> 理由は3つ。
> (1) 共有導線がスクショである以上、**音はスクショに乗らない**。MVPの目的である
>     バズ検証への寄与がない。
> (2) スマホはサイレントで開かれる割合が高く、本仕様自身がミュートボタンを
>     必須としている。**「聞こえない前提」を織り込んだ機能は主役になれない。**
> (3) 実装コスト(解錠・ミュート・10連打される効果音の音量調整)が演出本体より高い。
>
> **音を入れないため、ミュートボタンも廃止する。** ヘッダーはYロゴのみとする。
> 以下は Phase 1 以降に再検討する場合の参考仕様として残す。

ブラウザは **ユーザー操作なしに音を鳴らせない** ため、
投稿ボタンのタップを起点にAudioContextを解錠する設計が必須。

| 効果音 | タイミング | 方向性 |
|---|---|---|
| `post` | 投稿ボタン押下 | 短く軽い「シュッ」。ここでAudioContext解錠 |
| `reply_pop` | リプライ出現ごと | ポップな単音。連続再生されるため0.2s以内・音量控えめ |
| `yell_rise` | Phase C 開始 | 上昇する持続音。数字の加速と同期させる |
| `fanfare` | Phase D 完了時 | 短いファンファーレ。ソシャゲの報酬演出寄り |

- 音量は全体で控えめに。特に `reply_pop` は10連打されるため単体では小さすぎるくらいでちょうどよい
- ミュートボタンを画面右上に常時配置する(電車内で開く人が必ずいるため) ※Phase 0 では音ごと不採用
- 音源は自作 or ロイヤリティフリー素材。**ライセンス表記が必要なものは避ける**

## 9. スクショ映え要件

共有導線がスクショである以上、**「スクショした1枚が完成された画像になっている」** ことが機能要件になる。

- `settled` 状態で、投稿カード + リプライ上位3件が **1画面に収まる** こと
- 画面のどこかに控えめなアプリ名ロゴを常時表示(拡散時に出典が分かるように)
- 「保存する」ボタンは Phase 0 では置かず、**スクショを促す案内テキスト** で代替する。押しても何も起きないボタンは配置しない。画像生成(html2canvas等)とあわせてPhase 1で追加する
- **ライトテーマ(白背景)で作る。** エール数のピンク `#F91880` が画面内で唯一の強い色になるよう、他要素の彩度を抑える
