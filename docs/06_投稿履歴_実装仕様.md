# 投稿履歴 実装仕様書 v1.0

過去のポストを端末内に保存し、一覧・再生できるようにする。

- **作成**: 2026-08-20
- **実装担当**: Cursor
- **前提**: [02_X型演出_実装仕様.md](02_X型演出_実装仕様.md) の `ReactionScenario` がそのまま保存単位になる

---

## 1. なぜ今やるか

[01_要件定義.md](01_要件定義.md) 4章では履歴の蓄積を「後回し」に分類していたが、**MVPスコープに格上げする**。

理由は2つ。

1. **コアループが1回で終わってしまう。** 現状は「投稿 → 褒められる → もう一度」で、
   アプリを再訪する理由がない。過去の自分が褒められた記録が溜まることは、
   それ自体が再訪の動機になる。
2. **実装コストがほぼゼロ。** `buildScenario` は純粋関数で、出力の `ReactionScenario` は
   完全にシリアライズ可能な設計になっている(02章5節)。JSONにして保存し、
   読み戻して同じコンポーネントに流すだけで一覧も再生も成立する。

### スコープ外(Phase 1以降)

- サーバー保存・アカウント連携(**MVPは端末内のみ**)
- カレンダー表示・検索・タグ付け
- 履歴からの共有画像生成

## 2. 保存の方針

| 項目 | 決定 |
|---|---|
| 保存先 | **localStorage のみ。** サーバーには一切送らない |
| キー | `homarare:history:v1`(スキーマ変更に備えてバージョンを持たせる) |
| 保存タイミング | **`settled` に到達した時点で自動保存。** ユーザー操作は挟まない |
| 上限 | **50件。** 超えたら古いものから捨てる |
| 削除 | 1件削除と全削除の両方を用意する |

> **なぜ自動保存なのか**
> 「保存する」ボタンを押させると、押し忘れた回が消える。押した回だけ残る履歴は
> 「頑張った記録」として不完全で、溜まる喜びが弱くなる。
> 端末内にしか残らないので、自動で保存してもプライバシー上の危険がない。

> **なぜ localStorage で sessionStorage や IndexedDB ではないのか**
> タブを閉じても残る必要があるため sessionStorage は不可。
> 50件 × 約4KB = 約200KB で、localStorage の容量(5MB前後)の4%程度に収まるため
> IndexedDB を持ち出す必要がない。

## 3. データモデル

### 3-1. 事前リファクタ(必須)

現在の `ReactionItem.persona` は `Persona` 型で、**使わない `templates: string[]`(1人格あたり10件)を抱えている**。
そのまま保存すると1エントリあたり数KB増える。保存前に落とす。

```ts
/** リプライの表示に必要な情報だけを持つ。templates は含まない */
export interface ReplyAuthor {
  id: PersonaId;
  displayName: string;
  handle: string;
  avatarSrc: string;
  verified: boolean;
}

export interface ReactionItem {
  // ...既存のまま
  persona: ReplyAuthor;   // ← Persona から ReplyAuthor に変更
}
```

`Persona` は `lib/scenario/personas.ts` 側の定義として残す(テンプレートの持ち主として必要)。
`buildScenario` の中で `ReplyAuthor` に詰め替える。**UIが参照するフィールド名は変わらないので、コンポーネントの修正は不要。**

### 3-2. 履歴エントリ

```ts
export interface HistoryEntry {
  /** 保存時に採番する。crypto.randomUUID() */
  id: string;
  /** 投稿日時。ISO 8601 文字列で保存する（Date は JSON で復元されないため） */
  postedAt: string;
  /** 演出の完全な設計図。これ1つで再生できる */
  scenario: ReactionScenario;
}

export interface HistoryStore {
  version: 1;
  entries: HistoryEntry[];   // 新しい順
}
```

> **`postedAt` を Date ではなく文字列で持つ理由**
> `JSON.parse` は Date を復元せず文字列のまま返す。型は `Date` なのに実体は
> `string` という状態は、`toLocaleString()` を呼んだ瞬間に落ちる典型的なバグになる。
> **保存する型を最初から `string` にして、表示直前に `new Date()` する。**

## 4. 保存モジュール(`lib/history/storage.ts`)

Reactに依存しない純粋なモジュールとして作る(`lib/scenario/` と同じ方針)。

```ts
const KEY = "homarare:history:v1";
const MAX_ENTRIES = 50;

export function loadHistory(): HistoryEntry[];
export function saveEntry(scenario: ReactionScenario, postedAt: Date): void;
export function removeEntry(id: string): void;
export function clearHistory(): void;
```

### 必ず守ること

| 状況 | 挙動 |
|---|---|
| `typeof window === "undefined"`(SSR) | 何もせず空配列を返す。**例外を投げない** |
| JSONが壊れている / 型が違う | **その場でキーごと捨てて空配列を返す。**アプリは落とさない |
| `version` が想定と違う | 同上。将来のマイグレーションはここに書く |
| 容量超過(`QuotaExceededError`) | **古いエントリを削って再試行する。**それでも失敗したら諦めて握りつぶす |
| localStorage 自体が使えない(プライベートモード等) | try/catch で握りつぶし、履歴なしとして動作継続する |
| **`crypto.randomUUID` が存在しない** | **フォールバックのID生成に切り替える。**下記参照 |

> **`crypto.randomUUID()` をそのまま呼んではいけない**
> この API は**セキュアコンテキスト(https / localhost)でしか存在しない**。
> スマホ実機を `http://192.168.x.x:3000` で開いて確認するとき、
> `crypto.randomUUID` は `undefined` になり、呼んだ瞬間に TypeError で落ちる。
> **本番(https)では動くのに実機確認だけ壊れる**という気付きにくい形で出る。
> 必ず存在チェックとフォールバックを持たせ、`saveEntry` 全体も try/catch で囲む。

> **履歴の保存失敗でアプリを止めない。** 褒められる体験が本体であり、履歴は付随機能。
> ここで例外を投げると、演出が完走した直後に画面が壊れるという最悪の事故になる。

## 5. 画面設計

### 5-1. 遷移方針

[02_X型演出_実装仕様.md](02_X型演出_実装仕様.md) 2章の「**ルーティングによる画面切り替えは行わない**」は維持する。
履歴は**全画面オーバーレイ**として重ねる。`StageState` には手を入れない(演出の状態機械を汚さないため)。

```
Header（Yロゴ）
   └ 右端に履歴アイコン（lucide: History）← 新設
        ↓ タップ
   ┌──────────────────────────┐
   │ ← これまでのポスト     すべて削除 │  ← オーバーレイのヘッダー
   ├──────────────────────────┤
   │ 8月20日 午後10:23              │
   │ レポートを1ページ書いた           │
   │ ♡ 22,147   💬 429            │  ← カード。タップで詳細
   ├──────────────────────────┤
   │ 8月19日 午前7:02               │
   │ ...                          │
   └──────────────────────────┘
```

### 5-2. 一覧(`HistoryList`)

- **新しい順。** 日付は `8月20日 午後10:23` 形式(`lib/datetime.ts` を拡張して共通化する)
- 1件あたり: 日時 / 本文(2行でクランプ) / エール数 / リプライ数
- エール数は `like` 色・フル桁(03章6節のルールに従う)
- 各カードに削除ボタン(ゴミ箱アイコン)。**削除は即実行してよい**(取り消しは作らない)
- 空のとき: 「まだポストがありません」+ 「閉じる」で入力画面に戻す

### 5-3. 詳細(`HistoryDetail`)

タップすると、その回の**完成状態(`settled` 相当)を静止表示**する。

- 既存の `XPerformance` を再利用する。`metrics` に `scenario.targets` を、
  `visibleReplyIds` に全件のIDを渡せば、演出なしで完成形が出る
- **ハートバースト・カウントアップは動かさない。** 静止した1枚として見せる
- 下部に「もう一度再生」ボタン。押すと同じシナリオで12秒の演出を再生する
  → `buildScenario` を呼ばず、保存済みシナリオをそのまま `useReactionTimeline` に流す

### 再生時の必須ルール

| ルール | 理由 |
|---|---|
| **再生では履歴を保存しない** | 保存は「新しく投稿したとき」だけ。再生のたびに保存すると**同じポストが際限なく増殖し、50件の枠を自分で食い潰す** |
| `postedAt` は元の投稿日時を使う | 再生は過去のポストの再生であって、新しい投稿ではない |
| 再生開始時にオーバーレイを閉じる | 演出はアプリ本体の画面で見せる |
| `buildScenario` を呼ばない | 保存済みシナリオをそのまま流す。呼ぶと別物の演出になる |

> **再生機能を後回しにしてよい。**
> まず「一覧 → 静止した詳細」までを作り、動作を確認してから再生を足すこと。
> 再生は `StageContainer` の状態機械に触れるため、一覧より確実に難易度が高い。

## 7. 実装順序(Cursorへの依頼単位)

| Step | 内容 |
|---|---|
| 1 | **型リファクタ + 保存モジュール** — `ReplyAuthor` 導入と `lib/history/storage.ts`。UIなし。`settled` で保存されることを DevTools の Application タブで確認できる状態まで |
| 2 | **履歴一覧のオーバーレイ** — ヘッダーの履歴アイコン、一覧、削除、空状態 |
| 3 | **履歴詳細(静止表示)** — `XPerformance` の再利用 |
| 4 | **再生** — 保存済みシナリオで演出を再生する。ここだけ状態機械に触る |
